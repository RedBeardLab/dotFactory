A spec, not a runtime

Describe the workflow.
Not the implementation.

dotFactory is a small language for automations with and without AI agents. You write the dataflow — typed values moving through triggers, steps and sinks — and leave the object models, async runtimes and dependency-injection frameworks behind.

The problem

You are thinking in dataflow. You are writing everything else.

A trigger feeds a step, the step calls an agent, the output feeds another step, maybe a retry, then a sink. That picture is simple. But the moment you open an editor, the language makes you manage machinery that has nothing to do with it.

What you actually mean

  • The trigger admits a ticket.
  • The step drafts a result.
  • The reviewer approves or sends it back.
  • The sink writes the file.

What the language asks about

  • class hierarchies & metaclasses
  • interface satisfaction & goroutine lifecycle
  • ownership, borrowing, lifetimes
  • the event loop, the DI wiring, the framework
When the language fits the domain, the code becomes a direct translation of intent. Everything else follows from that.

The whole vocabulary

Eight concepts. No spare parts.

Every idea earns its place by being needed to describe how work flows through a graph. This is the entire language.

T

Type

Structural records. Fields and shapes — no classes, inheritance, or constructors.

type Ticket = { key: text }
▶

Trigger

Admits one seed value and holds it constant for the whole run. The host supplies the kind.

trigger start:
  kind: manual
▸

Step

Where work happens. Invokes a unit and binds its typed outputs.

step draft:
  runner: agent
⚙

Runner

How a step runs: a shell command, a container, or an agent behind a typed interface.

runner agent:
  kind: opencode
↦

Binding

Named edges that move values between ports. The bindings are the program.

in: { ticket: in.ticket }
⟲

Loop

A prev (loop-carried) binding re-fires a step with feedback — a retry, not control flow.

prev feedback: review.result
■

Sink

An effect. Inside a loop it fires each pass; downstream it fires once.

sink result:
  kind: file
⇥

External port

A bridge to the outside, implemented by the host. Secrets are opaque — redacted everywhere.

external port credential
  (key: text) -> secret

The execution model

A run is a round of firings until nothing can fire.

Press play. The trigger admits a ticket, the loop runs draft → review, the reviewer sends the draft back once, then approves. The progress sink fires inside the loop — once per pass — while result waits downstream and fires once.

uses credential port → secret agent opencode
start trigger draft step review step result sink
draft ⟵ prev feedback ⟵ review re-fires while not approved & under 3 attempts
in loop progress sink · each pass attempts recorded: 0
ready

Why a spec

Write the factory once. Host it anywhere.

The factory describes what should happen. The host supplies how: which trigger kinds exist, which runner backends run, where sinks write, how ports resolve. Those are adapter concerns — so they can compete without locking in your workflows.

# portable, self-describing
trigger start: kind: manual
step draft: runner: agent
sink result: kind: file
↔
  • Local — docker containers & the OpenCode server
  • Cloudflare — workers as steps, R2 as sink
  • AWS / GCP — Lambda/Batch steps, SQS triggers
  • Your own — register the kinds your domain needs

The spec defines the concepts; implementations follow. Tooling — validators, diagrammers, editors — can be built against the interface, independently of any one host.

Reference implementation

A parser, engine and host already exist.

The spec came first; a working slice now follows it. Validate a factory's shape, plan a run without calling any agent, then execute it against a host. 

# check the shape of a factory
uv run python -m fct  validate examples/minimal/factory.fct

# plan a run — no agent call, no side effects
uv run python -m host run  --factory examples/minimal/factory.fct \
  --trigger start --set 'ticket={"key":"ACME-1"}' --dry-run

# execute it for real (needs an OpenCode server)
FCT_CREDENTIAL_OPENCODE=… OPENCODE_SERVER_URL=http://127.0.0.1:4096 \
  uv run python -m host run --factory examples/minimal/factory.fct \
    --trigger start --set 'ticket={"key":"ACME-1"}' --exec local
fct/

Parser & validator

Parses the modules, resolves every reference and checks the spec's invariants.

engine/

Run engine

Drives a run as a round-based fixpoint over scopes — loops just re-fire through prev.

host/

Host & adapters

Binds runner, trigger, sink and port kinds, preflights them, and persists every run.
