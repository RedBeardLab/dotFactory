The problem

You are thinking in dataflow. You are writing everything else.

A trigger feeds a step, the step calls an agent, the output feeds another step, maybe a retry, then a sink. That picture is simple. But the moment you open an editor, the language makes you manage machinery that has nothing to do with it.

What you actually mean

  • The trigger fires on a GitHub issue.
  • The step drafts a reply.
  • The reviewer approves or sends it back.
  • The sink pings the team on Slack.

What the language asks about

  • class hierarchies & metaclasses
  • interface satisfaction & goroutine lifecycle
  • ownership, borrowing, lifetimes
  • the event loop, the DI wiring, the framework
When the language fits the domain, the code becomes a direct translation of intent. Everything else follows from that.

The core vocabulary

Eight concepts. No spare parts.

Every idea earns its place by being needed to describe how work flows through a graph. This is the core of the language; the rest is data, built-ins and host adapters.

T

Type

Structural records, lists and maps. Fields and shapes — no classes, inheritance, or constructors.

type Issue = { number: int }
▶

Trigger

Admits one seed value and holds it constant for the whole run. The host supplies the kind.

trigger issue_opened:
  kind: github
  config: { path: "/api/github/webhook", target: { one: { repo: "acme/widgets" } } }
▸

Step

Where work happens. Invokes a unit and binds its typed outputs.

step draft:
  runner: agent
⚙

Runner

How a step runs: a shell command, a container, or an agent behind a typed interface.

runner agent:
  kind: opencode
  in:   open
  out:  open
↦

Binding

Named edges that move values between ports. The bindings are the program.

in: { issue: in.issue }
⟲

Loop

A prev (loop-carried) binding re-fires a step with feedback — a retry, not control flow.

prev feedback: review.result
■

Sink

An effect. Inside a loop it fires each pass; downstream it fires once.

sink result:
  kind: file
  config: { path: "out/result.json" }
⇥

External port

A bridge to the outside, implemented by the host. Secrets are opaque — redacted everywhere.

external port credential
  (key: text) -> secret

Beyond the loop

Small language. Sharp edges.

The retry is the execution model. These are the everyday features that keep the factory small: collections without loops, open-keyed data, absence that cannot be confused with null, and configuration that lives with the deployment.

The execution model

A run is a round of firings until nothing can fire.

Press play. The trigger admits a GitHub issue, the loop runs draft → review, the reviewer sends the draft back once, then approves. The progress sink fires inside the loop — once per pass — while comment waits downstream and posts once.

Why a spec

Write the factory once. Host it anywhere.

The factory describes what should happen. The host supplies how: which trigger kinds exist, which runner backends run, where sinks write, how ports resolve. Those are adapter concerns — so they can compete without locking in your workflows.

# portable, self-describing
trigger issue_opened: kind: github · event: issues
loop reply: draft ⇄ review
sink comment: kind: github_issue
↔
  • Local — the reference host: containers & OpenCode
  • Cloudflare — workers as steps, R2 as a sink (adapter)
  • AWS / GCP — Lambda/Batch steps, SQS triggers (adapter)
  • Your own — register the kinds your domain needs

The spec defines the concepts; implementations follow. Tooling — validators, diagrammers, editors — can be built against the interface, independently of any one host.
